## 2. 根因分析

### 2.1 `AgentRunner.executeTool` 直接把流中间态参数丢给了 Spring AI

`executeTool`（修复前第 347 行）：

```java
String result = callback.call(toolCall.arguments());   // ← 直接交给 MethodToolCallback
```

**Spring AI 1.0.0-M6 的 `MethodToolCallback.call(String)` 内部**：

```java
// org.springframework.ai.tool.method.MethodToolCallback#call(String)
Map<String, Object> args = JsonParser.fromJson(arguments, Map.class);   // ← 这里抛异常
return methodCallExecutor.execute(method, args, toolContext);
```

→ 一旦 `arguments` 不是合法 JSON（中间态、流尾巴截断），Jackson 直接 `JsonEOFException: Unexpected end-of-input in field name`，并被 Spring AI 包装成 `IllegalStateException` 抛出。

我们的 `catch (Exception e)` 兜住异常，发出 `TOOL_CALL_FAILED` + 把错误回传给模型。但**根问题没解决**：下一轮模型可能又吐出截断 JSON，又一次失败 → 看上去就是连续失败。

### 2.2 连续 3 次 `工具未注册 tool=null` 的成因

修复前的 `handleChunk` 第 240-244 行：

```java
if (output.hasToolCalls() && output.getToolCalls() != null && !output.getToolCalls().isEmpty()) {
    ctx.toolCalls = output.getToolCalls();   // 直接覆盖，未做字段完整性校验
}
```

流式响应中可能存在两类 ToolCall：

1. **完整版**：`id`、`name`、`arguments` 都已填好
2. **中间态**：仅填写了部分字段（典型场景：Qwen turbo 的 tool_call delta 链，前几个 chunk 只填 id 和 arguments 的一小段）

旧代码用 `=` **直接覆盖** `ctx.toolCalls`，导致：
- 中间态的 ToolCall 完整版丢失前仍短暂留存
- `executeTool` 遍历 `ctx.toolCalls` 列表时，遇到 `name == null` 的 ToolCall 报 `未找到可用的工具`
- 多个中间态 ToolCall 同时存在时，出现多次 `tool=null`

### 2.3 为什么 Qwen 会吐出 `{"request` 这种残段

`OpenAI` 兼容流协议下 `tool_calls[].function.arguments` 是**字符串增量**：模型分多次输出，每次只追加一段。

在我们使用的 **Qwen turbo + DashScope 兼容模式**下：

- 多数情况下模型一次性输出完整 JSON → 流末尾 arguments 完整
- 少数情况（特别是 prompt 复杂度高、上下文较长）下，模型在 tool_call 中途戛然而止，arguments 一直是半截 JSON 就走到流结束

`AgentRunner` 之前没有任何"参数是否完整"的校验，把控制权直接让给 Spring AI → Spring AI 拋 `IllegalStateException`。

### 2.4 错误传播链路（修复前）

```
Qwen 流结束
  → AssistantMessage.getToolCalls() 仍持有"中间态/截断 JSON"
  → AgentRunner.executeTool 遍历 ctx.toolCalls 调 callback.call(截断 JSON)
    → MethodToolCallback.extractToolArguments JSON→Map 抛 JsonEOFException → 包 IllegalStateException
  → AgentRunner catch → 发 TOOL_CALL_FAILED，错误回传模型
  → 模型下一轮再次尝试 tool_call（同病）
  → 日志里就看到反复的"工具未注册 tool=null / 转换失败"
```

## 3. 修复方案

> 最小侵入、零协议变更：仅在 `AgentRunner` 内部加防御性过滤，不改 SSE 事件类型、不改前端。

### 3.1 过滤 + 去重：在 `handleChunk` 合并入 ctx 之前先校验完整性

新增静态方法 `mergeCompleteToolCalls(List<ToolCall>, RoundCtx)`：

- 用 `LinkedHashMap<id, ToolCall>` 按 id 合并，**后到的完整版本覆盖同一 id 的早期版**（OpenAI 兼容协议下流末尾才是完整版）
- 合并前用 `isCompleteToolCall(tc)` 过滤掉不完整的

新增静态方法 `isCompleteToolCall(ToolCall)`：

- `id` / `name` / `arguments` 均非空白
- `arguments` 能被 Jackson `readTree(...)` 解析为合法 JSON（单节点即可）

任何**不满足以上条件**的 ToolCall 在合并阶段被剔除，不进入 `ctx.toolCalls`。

### 3.2 兜底：在 `executeTool` 入口再做一次校验

即便上游路径未来变更（例如直接复用 ctx 字段），`executeTool` 入口仍调用 `isCompleteToolCall` 校验一次。

- 通过：进入原有"查找 callback → 调用"逻辑
- 失败：记录 WARN 日志 (`跳过不完整工具调用 id=... name=... args=...`)，**不发任何事件、不回传错误给模型**，避免死循环

### 3.3 关键代码片段

`AgentRunner.java`（修改涉及文件 +580/-3 +91）：

```java
// 新增私有常量 + Jackson 工具
private static final ObjectMapper JSON = new ObjectMapper();

// handleChunk：原覆盖式赋值改为合并+过滤
if (output.hasToolCalls() && output.getToolCalls() != null && !output.getToolCalls().isEmpty()) {
    mergeCompleteToolCalls(output.getToolCalls(), ctx);
}

// executeTool：入口兜底
if (!isCompleteToolCall(toolCall)) {
    log.warn("[agent] 跳过不完整工具调用 id={} name={} args={}",
            nullToEmpty(toolCall.id()), nullToEmpty(toolCall.name()),
            truncate(toolCall.arguments(), 80));
    return Flux.fromIterable(events);
}

// 两个静态辅助方法：合并 + 完整性判定
private static void mergeCompleteToolCalls(...) { /* 按 id 去重 + 过滤 */ }
static boolean isCompleteToolCall(AssistantMessage.ToolCall tc) {
    if (tc == null) return false;
    if (isBlank(tc.id()) || isBlank(tc.name()) || isBlank(tc.arguments())) return false;
    try { JSON.readTree(tc.arguments()); return true; }
    catch (Exception e) { return false; }
}
```

### 3.4 设计选择说明

- **过滤而非解析**：选择丢弃不完整 ToolCall，而不是"等几毫秒看后续 chunk"。原因：流末尾时机的判断需要进入"流已结束"分支，强行延后会破坏 `Flux` 拓扑；过滤路径上更简洁。
- **不绕过 `MethodToolCallback`**：未直接反射调工具方法。原因：保留 Spring AI 拦截器（如未来加 `ToolCallBackFilter` 等扩展）的能力，**仍是 Spring AI 第一次接到 `callback.call` 时参数完整**。
- **不修改 system_prompt**：不把"必须输出完整 JSON"加进提示语。原因：靠 prompt 兜底未根治；问题应在协议层处理。

2. **更激进的方法**：直接绕开 `MethodToolCallback`，在 `AgentRunner` 里手动反序列化 JSON 到 DTO（如 `WeatherRequest`），再用反射调 `WeatherTool.getWeather(...)`。优点：参数错误能被前置 fail-fast；缺点：失去 Spring AI interceptor 链。**当前修复已足够稳健，无需引入**。

### 反思（供后续 review）

- **为什么不早拦截？** 历史上的 `AgentRunner.stream()` 设计假设 "OpenAI 兼容流的最后一个 chunk 会给出完整 arguments"（注释里写过）。事实是 Qwen turbo 在 tool_call 路径上偶尔不补完就结束——注释没体现这一观察。已在本修复中更新该注释，明确指出"部分模型会把中间态 ToolCall 也塞进列表"。
- **是否可以让 model 自己修复？** 当前 system_prompt 没要求 model 在 tool_call 前重排参数。可在 prompt 中追加一句：`必须一次性输出完整的 JSON 参数；若参数复杂请将整段 JSON 一次输出`，让 Qwen 收敛。**建议：同步在 prompt 里强化，而不是改代码**。本修复不动 system_prompt。

## 7. 二次修复：把"工具调用阶段"留给模型重试

> 时间：2026-09-07 08:30　|　触发：用户反馈"仍然无法正常输出"

### 7.1 第一版修复的副作用

第一版（§3）采用"过滤即丢弃"的语义：`mergeCompleteToolCalls` 把 `isCompleteToolCall=false` 的 ToolCall 全部不入 `ctx.toolCalls`。

复现日志（截取）：

```
08:28:44.755  收到流式请求 ... question=北京今天天气怎么样？适不适合出门？
08:28:44.755  完成 sessionId=... 耗时=531ms tokens=prompt=856,completion=10 err=null
08:29:30.852  ... 耗时=657ms tokens=prompt=723,completion=33 err=null
08:29:37.832  ... 耗时=496ms tokens=prompt=752,completion=23 err=null
```

前端截图（截取）：

```
思考过程 [1]
  需要先查询北京的实时天气。
（本轮无文本输出）
⏱ 530ms · ⚡ 866 tokens
```

**症状解读**：

- 模型在第一轮先输出 `思考：需要先查询北京的实时天气。`（被剥到 `ctx.splitter`），
- 紧跟一次 tool_call `getWeather`，但 `arguments` 是被截断的 JSON。
- 第一版修复：ToolCall 因 isCompleteToolCall=false 被丢弃 → `ctx.toolCalls == null`。
- `afterRound` 进入"最终答案轮"分支 → `finalText = ctx.rawText.toString().trim()`，
  但 rawText 在本轮只有"思考："那一行（被分类器拦截后没形成正文）→ finalText 非空但被当作"思考"已结。
- 模型因此没有"工具响应信号"作为下一步输入 → 收尾直接空。
- 前端：思考过程 + "本轮无文本输出" + 没有任何 DATA 任何 Tool Call 卡片。

经验：`args={"request` 这种中间态 ToolCall 是**模型的真实意图**，把它直接当作"从未发生"会让对话断路。

### 7.2 第二版修复的策略

把"工具调用阶段"视为**对模型可见的失败回放**，而不是"对模型隐藏的丢包"：

| 项 | 第一版 | 第二版（当前） |
|---|---|---|
| 中间态 ToolCall 是否进 `ctx.toolCalls` | 否 | **是**（让 afterRound 走"工具调用轮"） |
| 中间态 ToolCall 的 UI 表现 | 啥都没有 | STARTED → FAILED（完整生命周期） |
| 是否回传 ToolResponse 给模型 | 否 | **是**（"请重新输出完整 JSON 参数"，让下一轮修正） |
| 模型下一轮表现 | 没有机会修正、直接结束 | 拿到"失败信号" → 重生成/兜底 |
| Spring AI 是否抛 `IllegalStateException` | 否 | 否（不调 `callback.call(截断JSON)`） |
| `MethodToolCallback` 是否被正确路径调 | 是（完整时） | 是（完整时）；中间态完全跳开 |

### 7.3 代码改动（diff-by-section）

#### 7.3.1 `mergeCompleteToolCalls`：保留中间态作为兜底

```java
// 新规则：完整版覆盖中间态；中间态也保留一份占位让 afterRound 走"工具调用轮"
for (AssistantMessage.ToolCall tc : incoming) {
    if (tc == null || tc.id() == null || tc.id().isBlank()) continue;
    AssistantMessage.ToolCall prev = merged.get(tc.id());
    if (prev == null) {
        merged.put(tc.id(), tc);                          // 第一次入 → 直接放
    } else if (!isCompleteToolCall(prev) && isCompleteToolCall(tc)) {
        merged.put(tc.id(), tc);                          // 中间态 → 完整：用完整覆盖
    }
    // 其它一律不覆盖（避免来回震荡 / 完整版被新中间态劣化）
}
```

#### 7.3.2 `executeTool`：补"参数截断"分支

```java
// 修改前：第一道关卡的 if (!isCompleteToolCall) 直接 return，空事件列表
// 修改后：无论是否完整都先发 STARTED，让 UI 看到一致的工具调用卡片
events.add(buildEvent(TOOL_CALL_STARTED, Map.of(...)));
...
if (!isCompleteToolCall(toolCall)) {
    // 极少见，但 UI 仍能看到"调用 → 失败"完整周期；同时把"参数不完整"回传给模型
    events.add(buildEvent(TOOL_CALL_FAILED, Map.of("toolName", ..., "error", "...")));
    toolResponses.add(new ToolResponseMessage.ToolResponse(
        toolCall.id(), nullToEmpty(toolCall.name()),
        "工具调用失败：工具调用参数不完整（流中模型输出的 arguments 被截断），请重新输出完整 JSON 参数"));
    return Flux.fromIterable(events);
}
```

这样做的两个关键不变量：

1. **`ctx.toolCalls.size() == toolResponses.size()`**：满足 OpenAI 协议对工具响应数量的要求，否则下一轮 LLM 请求会被拒绝。
2. **不调 `callback.call(截断JSON)`**：Spring AI 的 `IllegalStateException` 永远不会发生。

### 7.4 单测补充（`AgentRunnerTest`）

| 用例 | 验证场景 | 关键断言 |
|---|---|---|
| `stream_truncatedToolCallArguments_emitsStartedFailedAndLeavesRoomForRetry` | args = `{"request` 截断 | STARTED×1 + FAILED×1；RESULT×0；`weatherCallback.call` not called；chatModel.stream 被调两次 |
| `stream_toolCallWithNullName_emitsStartedFailedAndLeavesRoomForRetry` | name = null | 同上（name= 路径） |
| `stream_duplicateToolCallId_keepsLatestCompleteInvocation` | 同 id 先空后完整 | STARTED×1 + RESULT×1 + FAILED×0；`weatherCallback.call` 一次 |

## 11. 五次修复（v5）：abort 路径下 finalText 不再吃 rawText 的"思考："行

> 时间：2026-09-07 09:45　|　触发：用户 09:45 / 09:56 两次复现

### 11.1 现象（用户日志 + 截图）

服务端日志：

两次复现行为一致：从 WARN 到完成仅隔 ~4ms，**没有出现** `WARN 模型未输出最终答案，使用兜底文字 sessionId=...` —— 说明 v4 的 fallback 文字路径**没触发**。

前端截图：

```

  失败原因   ⚠ 工具调用失败: 参数 JSON 被流式截断（不完整），无法调用工具。
```

### 11.2 根因

v4 的 `persistFinalAnswer`：

```java
String finalText = ctx.rawText.toString().trim();   // ← 这里吃 rawText
if (finalText.isEmpty()) { finalText = FIXED_FALLBACK; ... }
```

在 abort 真实场景里，模型几乎必然先输出一行「思考：xxx」（被 splitter 抽走发 REASONING），然后才声明截断的 tool_call。此时 `rawText` 仍然完整包含「思考：xxx」原文，**不为空**，于是：

- 跳过 fixed fallback 文字；
- 直接 `dataEvent("思考：需要先查询北京的实时天气。")` → 前端把这个当成最终答案 DATA 渲染；
- 用户体感 = "思考过程回放 + 无答案"，跟 v4 修复前的 v2 几乎一样糟。

**为什么 v4 单测没抓到**：现有 `stream_truncatedToolCallArguments_emitsStartedFailedThenFallsBackWithoutRetry` 用的是 `chunkWithToolCall` 工具（文本字段是 `""`），rawText 天然为空，所以 fallback 文字路径触发正常，**掩盖了 rawText 非空时也会落入 DATA 事件的这条分支**。

### 11.3 v5 修复

核心思路：**abort 路径下 finalText 不应取 rawText**，而应取「splitter 已剥离思考行后累计的纯正文」。这条路径下 splitter 没有 data 增量（模型在思考后直接出 tool_call），`dataOnlyText` 必然为空，正好走到 fixed fallback。

#### 11.3.1 `RoundCtx` 新增 `dataOnlyText`

```java
private static final class RoundCtx {
    final StringBuilder rawText = new StringBuilder();
    /** 仅含 DATA 增量的累计（splitter 在 emitData 时同步写入） */
    final StringBuilder dataOnlyText = new StringBuilder();
    /** 「思考：」行分类器（同步把 DATA 增量写到 dataOnlyText） */
    final ReasoningSplitter splitter = new ReasoningSplitter(dataOnlyText);
    ...
}
```

#### 11.3.2 `ReasoningSplitter` 接受外部 sink

构造新增重载；`emitData` 时除了 `events.add(dataEvent(...))` 也把同一段文本 append 到 sink：

```java
ReasoningSplitter(StringBuilder dataSink) { this.dataSink = dataSink; }

private void emitData(List<ChatEventVO> events) {
    if (data.length() > 0) {
        String s = data.toString();
        events.add(dataEvent(s));
        if (dataSink != null) { dataSink.append(s); }   // 同步外部 sink
        data.setLength(0);
    }
}
```

兼容老的 `new ReasoningSplitter()`（无 sink 模式，dataSink=null）——目前没人在用，留作防御。

#### 11.3.3 `persistFinalAnswer` 在 aborted 时换取值源

```java
private ChatEventVO persistFinalAnswer(AgentTurn turn, RoundCtx ctx) {
    // abort 路径：rawText 必含「思考：」行，不能原样当 DATA 重发 → 改用 dataOnlyText
    String finalText = (ctx.aborted ? ctx.dataOnlyText : ctx.rawText).toString().trim();
    if (finalText.isEmpty()) {
        finalText = FIXED_FALLBACK;
        log.warn("[agent] 模型未输出最终答案，使用兜底文字 sessionId={}", turn.conversationId);
    }
    try { chatMemory.add(...); } catch (Exception e) { log.error(...); }
    return dataEvent(finalText);
}
```

正常路径完全不变（`aborted=false` 时仍取 rawText，与 v4 行为一致）；abort 路径下 `dataOnlyText` 必空 → 必走 fixed fallback。

`stream_abortedAfterThinkingLine_emitsReasoningThenFallbackNotReasoningEcho`：先发 `chunk("思考：需要先查询北京的实时天气。\n", ...)`，再发 `chunkWithToolCall(..., truncated args)`，断言：

| 断言 | 含义 |
|---|---|
| `REASONING` 事件恰好 1 条，data=`"需要先查询北京的实时天气。"` | splitter 正常剥离思考行 |

### 11.7 反思（v4 → v5）

1. **v4 的兜底逻辑只覆盖了 `finalText.isEmpty()` 这一支**：当 rawText 非空但其内容是已发过 REASONING 的「思考：」行时，v4 直接把这条原文当 DATA 重发，等于把"过程"包装成"答案"。**单测用 `chunkWithToolCall`（text=""）掩盖了这条分支**。

3. **真实环境比 mock 更严格**：测试覆盖到「调用了一次还是两次」「STARTED/FAILED/RESULT 计数」但没覆盖到「DATA 内容到底来自 rawText 还是 dataOnlyText」——一个内容层面的不变量被忽略了。下次类似 BUG 应在测试里至少加一条 `notContains` 类断言。
4. **真实环境中 abort 路径必含「思考：」行**：模型要 tool_call 几乎必然先做意图说明 → 真实 abort 路径下 rawText 必然非空 → v4 修复在真实环境下**总是**落入错分支。这是个 v4 设计时就漏掉的"伪 empty"边界。

## 13. 六次修复（v6）：治本——扁平化 schema + 非流式截断恢复

> v1–v5 五版都在「把兜底文案做得更漂亮」，从未触及根因。v6 是第一次真正治本：
> 从源头降低截断概率，并让截断后能**恢复出真实答案**而非固定兜底。

### 13.1 真正的根因（为什么前五版治不了）

1. **单参 DTO 被 Spring AI 包成嵌套 schema**：`weatherTool.getWeather(WeatherRequest request)` 中，Spring AI `JsonSchemaGenerator.generateForMethodInput` 按**方法参数名**作为 JSON 对象 key，单个 record 参数会生成 `{"request":{"city":"..."}}` 而非扁平的 `{"city":"..."}`。模型每次 tool_call 都要多输出一层 `{"request":...}` 的 token。
2. **qwen-turbo 流式截断 arguments**：`tool_calls[].function.arguments` 是字符串增量，复杂 prompt 下模型中途戛然而止，arguments 停在半截 JSON（如 `{"request`）。token 越多、越嵌套，越容易截断。

前五版都在「截断发生后」做文章（丢弃 / 回传重试 / 兜底文案），截断本身一次都没减少。

### 13.2 v6 三层修复

#### ① 扁平化工具入参（源头，治本）

- `weatherTool`：删除 `WeatherRequest` record，改为 `getWeather(@ToolParam(description="要查询天气的城市名称，例如 北京") String city)`。
- `attractionTool`：删除 `AttractionRequest` record，改为 `getAttraction(@ToolParam(description="城市名称，例如 北京") String city, @ToolParam(description="当前天气描述，例如 晴 26℃") String weather)`。
- 效果：schema 变 `{"city":"北京"}`（扁平），token 减半，截断概率显著下降。

#### ② system_prompt 加固

追加规则 5：「调用工具时，参数 JSON 必须一次性完整输出（例如 {"city":"北京"}），不要分多次、不要中途截断。」

#### ③ 非流式截断恢复（安全网）

截断仍可能发生（偶发、不可 100% 消除）。此时不再走 v4/v5 的「abort → 固定兜底」，改走 `recoverTruncatedTurn`：

- `executeTool` 判定中间态（id/name/arguments 不全或 arguments 非 JSON）→ 发 STARTED + FAILED 卡片，置 `RoundCtx.truncated=true`（原 `aborted`）。
- `afterRound` 见到 `truncated` → 调 `recoverTruncatedTurn`：**干净重建**上下文（system + 历史 + user + 一条纠正 SystemMessage「参数未完整输出，请重新调用工具并一次性输出完整 JSON」），用 `chatModel.call(Prompt)`（**阻塞、非流式**）重取。
- 非流式 call 等模型完整输出后才返回，arguments 不会像流式那样被中途截断。恢复结果三分支：
  1. 模型直接给文字 → `finalizeAnswer(文字)`（真实答案）；
  2. 模型重新声明完整工具调用 → 执行工具 + 第二次 call 拿答案（真实答案）；
  3. 仍截断 / 抛异常 → `finalizeAnswer(null)` → fixed fallback。
- 关键点：**不把首轮半截 JSON 回传模型**（那是 v2/v3 把 Qwen 诱导成空流的诱因），而是干净重建。

### 13.3 删除冗余（瘦身）

v6 顺带删掉了 v5 引入、现已被恢复路径取代的机制：

- `RoundCtx.dataOnlyText` 与 `ReasoningSplitter.dataSink` 删除；`ReasoningSplitter` 回到无参单构造器。
- `RoundCtx.aborted` 改名 `truncated`（语义更准：截断，而非中止）。
- `persistFinalAnswer` 简化为 `finalizeAnswer(turn, ctx.rawText)`：正常最终答案轮的 rawText 必不含「思考：」行（思考行只出现在 tool_call 轮），v5 的 rawText/dataOnlyText 分流不再需要。

### 13.4 单测重写（3 个截断用例 → 恢复语义）

| 用例 | 场景 | 关键断言 |
|---|---|---|
| `stream_truncatedToolCallArguments_recoversViaNonStreamingCall` | 截断 → 恢复直接给文字 | `call` times(1)；DATA 是真实答案；记忆写回真实答案 |
| `stream_toolCallWithNullName_recoversByRecallingTool` | name 缺失 → 恢复重调工具 | `call` times(2)；STARTED×2 + FAILED×1 + RESULT×1；`weatherCallback.call` 一次 |
| `stream_abortedAfterThinkingLine_recoversButFallsBackWhenStillTruncated` | 思考行 + 截断 → 恢复仍截断 | STARTED×2 + FAILED×2；DATA 是 fixed fallback 且不含「思考：」 |

### 13.5 测试结果

`mvn -o test` **20/20** 全过（AgentRunnerTest 9 + ChatServiceImplTest 10 + AgentDemo10ApplicationTests 1），BUILD SUCCESS。

### 13.6 反思（五版症状修复 → 一次治本）

1. **前五版的共同失误**：都在「截断发生后」美化兜底，没想过「减少截断」本身。真正的杠杆在**源头**（扁平 schema 减 token）和**恢复机制**（非流式 call 绕开流式截断）。
2. **恢复优于兜底**：v4/v5 用固定兜底文案，把「会返回什么」从模型行为变成确定行为——这确实稳定，但也意味着用户**永远拿不到真实答案**。v6 的恢复让「真实答案」成为主路径，兜底只作为最后保险。
3. **非流式 call 是绕开流式截断的干净手段**：流式截断的根源是「边生成边输出」，非流式 call 天然等完整输出，从机制上免疫。
